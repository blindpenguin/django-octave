# Requirements Document

## Introduction

Three functions edit a project's configuration files with regular expressions and string searches:

- `patch_urls(urls_path, app_name)` in `project/patch.py`, used by `add`, adds `path("api/", include("apps.<app>.urls"))` to `config/urls.py`.
- `patch_installed_apps(settings_path, dotted_app)` in the same module, used by `add`, adds the app to `INSTALLED_APPS` in `config/settings/base.py`.
- `patch_urls(root, include_register)` in `frontend_gen/django_patch.py`, used by `add-frontend` and `new --frontend`, swaps the token view, wires the user list and the optional register route, and manages an import block.

`docs/code-audit-2026-11-23.md` (section 3, item 4) calls this brittle. Trying realistic edits to a generated project confirms it, and finds failures worse than the audit describes:

| Edit to the project | `add` | `add-frontend` |
|---|---|---|
| `path()` calls wrapped by a formatter (trailing comma) | works | fails: "Could not find api/auth/token/ path" |
| parenthesized multi-line imports | **exits 0, `urls.py` left unparseable** | writes a `urls.py` that does not parse |
| single-quoted strings | works | fails: "Could not find api/auth/token/ path" |
| a `]` inside a string in the list | **exits 0, `urls.py` left unparseable** | works |
| last route without a trailing comma | **exits 0, `urls.py` left unparseable** | works |
| `urlpatterns` on one line | **exits 0, `urls.py` left unparseable** | not applicable (needs the token routes) |
| `urlpatterns: list = [` | fails ("Could not locate urlpatterns") | works |
| `INSTALLED_APPS` on one line | **exits 0 and appends the app to `MIDDLEWARE`** | not applicable |
| `INSTALLED_APPS` as a tuple, or with a type annotation | fails ("Could not locate INSTALLED_APPS list") | not applicable |

Each cell was measured on its own fresh copy of a generated project (an earlier draft of this table ran both commands on the same copy, so the second command read a file the first had already corrupted). Five of the cases are silent: a successful exit with a broken or wrongly edited project. A sixth problem showed up while capturing golden files: when the user has wired the register route by hand, a second `add-frontend` run adds a duplicate register route and import. `add` is also not all-or-nothing: it renders the app and patches settings before it patches URLs, so a later failure leaves a half-added app.

This spec rewrites the three functions to edit the syntax tree with libcst (already a dependency, already used by `models_gen/`), so formatting, quoting and wrapping stop mattering. When a file has a shape that cannot be understood, the command fails with a message that says exactly what to add by hand and writes nothing. It also makes `add` all-or-nothing.

Out of scope: the app-level `urls.py` router registration (`ensure_router_registration`), the `.env` patches, and generating different content than today.

## Alignment with Product Vision

django-octave edits files the user owns and reformats. A patcher has to cope with that or refuse clearly; it must never report success and leave a project broken.

## Requirements

### Requirement 1 — The urls patchers read the file's structure, not its text

**User Story:** As a developer who runs a formatter or edits `config/urls.py`, I want `add` and `add-frontend` to keep working, so that my formatting choices do not break the generator.

#### Acceptance Criteria

1. WHEN `config/urls.py` uses single quotes, double quotes, or a mix THEN both `patch_urls` functions SHALL find and edit the right routes, and anything they add SHALL use the quote style of the existing routes (double quotes when there is no precedent).
2. WHEN `path()` calls are wrapped over several lines, with or without a trailing comma THEN they SHALL be found and edited correctly.
3. WHEN the `django.urls` or `rest_framework_simplejwt.views` imports are on one line, in parentheses over several lines, or in a different order THEN the needed names SHALL be added (or removed, for the simplejwt obtain view) without producing an invalid file.
4. WHEN `urlpatterns` is assigned with a type annotation (`urlpatterns: list = [...]`) THEN it SHALL be found.
5. WHEN the file contains brackets, quotes or the text of a route inside comments or string literals THEN they SHALL be ignored.
6. WHEN the file has other routes, comments, blank lines, or extra `urlpatterns += [...]` blocks THEN everything the patch does not need to change SHALL stay byte-identical.

### Requirement 2 — Files generated by django-octave get exactly the same result

**User Story:** As a user of an unmodified project, I want nothing to change.

#### Acceptance Criteria

1. WHEN `add` or `add-frontend` (with and without register) run on a freshly generated project THEN `config/urls.py` and `config/settings/base.py` SHALL be byte-identical to what the current code produces, including the managed import block with its begin and end comment lines, except that `add` no longer leaves the stray blank line before the closing `]` of `INSTALLED_APPS` that the old patcher produced (decided while implementing: one blank line fewer in `settings/base.py`).
2. WHEN a project was patched by an earlier version (the managed import block is already there) THEN re-running the command SHALL update that block in place, add no duplicate import, and change nothing when nothing needs to change.
3. WHEN any patch runs twice with the same input THEN the second run SHALL change nothing and `patch_urls` / `patch_installed_apps` SHALL report that (`False` for the `add` patchers, the same file unchanged for the frontend patcher).
4. WHEN the register route or the user list is already wired by hand (a route to `api/auth/register/` or `api/users/` that is not managed) THEN the frontend patcher SHALL NOT add a second one, as today; "already wired" SHALL be decided from the routes, not from text in comments.

### Requirement 3 — `INSTALLED_APPS` is edited in the right list

**User Story:** As a developer, I want a new app registered in `INSTALLED_APPS` and nowhere else.

#### Acceptance Criteria

1. WHEN `INSTALLED_APPS` is a list or tuple literal, on one line or several, with or without a trailing comma, with comments, with single or double quotes, plain or with a type annotation THEN `patch_installed_apps` SHALL add the app as its last element, in the style of the existing entries, and SHALL change nothing else.
2. WHEN the file defines other lists after or before it (`MIDDLEWARE`, `AUTH_PASSWORD_VALIDATORS`, ...) THEN they SHALL NOT be touched.
3. WHEN the app is already a string element of a list or tuple in the file THEN the patch SHALL do nothing and return `False`; the app name appearing only in a comment or another kind of string SHALL NOT count.
4. IF `INSTALLED_APPS` is built in a way that cannot be edited (for example `DJANGO_APPS + LOCAL_APPS`) and the app is not already listed THEN `PatchError` SHALL tell the user which line to add to which file, and nothing SHALL be written.

### Requirement 4 — What cannot be understood fails loudly and writes nothing

**User Story:** As a developer, I want a clear message and an untouched project when the patcher does not understand my file.

#### Acceptance Criteria

1. WHEN `urlpatterns` is missing or is not a list literal THEN `add` SHALL fail with `PatchError` naming the file and giving the exact line to add (`path("api/", include("apps.<app>.urls")),`) and the import it needs, and no file SHALL change.
2. WHEN `add-frontend` cannot find the token route (`api/auth/token/`) or the refresh route (`api/auth/token/refresh/`) THEN it SHALL fail with `DjangoPatchError` naming the route it looked for and what it was going to do with it, and no file SHALL change.
3. WHEN a file cannot be parsed as Python THEN the error SHALL name the file and the syntax problem, and the file SHALL stay unchanged.
4. WHEN a patch is computed THEN the new text SHALL be parsed again before it is written; a result that does not parse SHALL never be written.

### Requirement 5 — `add` is all-or-nothing

**User Story:** As a developer, I want a failed `add` to leave my project as it was.

#### Acceptance Criteria

1. WHEN `add` fails after it started writing (for example the URLs patch is refused after the app was rendered and settings were patched) THEN the project SHALL be restored (`rollback_on_error`): no app directory, no settings change, no urls change.
2. WHEN `add` succeeds THEN the output, files and messages SHALL be as today.
3. WHEN the failure is one of the loud errors of Requirement 4 THEN the command SHALL exit with code 1 and print the message without a traceback.

### Requirement 6 — Documentation and records

**User Story:** As a user, I want to know what to do when patching is refused.

#### Acceptance Criteria

1. WHEN the docs are built THEN `docs/commands/add.md` and `docs/commands/add-frontend.md` SHALL say which file shapes are understood, that other shapes are refused with the exact manual step, and that nothing is written in that case.
2. WHEN this spec is implemented THEN the audit notes SHALL mark item 4 done and record the two silent failures that were found.

### Requirement 7 — Nothing else changes

**User Story:** As a user, I want the generator otherwise unchanged.

#### Acceptance Criteria

1. WHEN the full suite and the opt-in e2e suites run THEN they SHALL pass without weakening an existing test, and `tests/commands/test_option_probe.py` SHALL still pass.
2. WHEN a reference project is generated from `HEAD` and from the new code (same launch method on both sides) THEN the two trees SHALL be identical, apart from that one blank line in `config/settings/base.py` when the reference project runs `add`.
3. WHEN the public functions are called THEN their names, signatures, return values and the exception types (`PatchError`, `DjangoPatchError`, both `OctaveError`) SHALL stay the same.

## Non-Functional Requirements

### Code Architecture and Modularity
- **Single Responsibility Principle**: the libcst helpers that find a list, add an element, add or remove an import name and report a shape problem live in one module; the three functions only say what to change.
- **Modular Design**: the helpers work on a libcst `Module` and do no file I/O, so they are unit-testable on strings.
- **Dependency Management**: libcst only (existing dependency); no new dependency.
- **Clear Interfaces**: fully annotated; errors carry the file name and the manual step.

### Performance
- A config file is a few dozen lines; one parse per patch.

### Security
- Strings written into a file are either fixed text or validated names (`validate_app_name` already runs before `add` patches anything); no raw user text reaches a file.

### Reliability
- Nothing is written unless the whole patch succeeded and the result parses. `add` is all-or-nothing.

### Usability
- Every refusal says what to do by hand, with the exact line and file.
