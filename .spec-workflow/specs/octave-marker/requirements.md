# Requirements Document

## Introduction

A generated project does not say which django-octave made it or which options were chosen. Every `add-*` command therefore re-derives the project's shape by looking at files (three heuristics for multitenancy, `config/celery.py` or a settings grep for Celery, the `frontend/` directory for the SPA), and nothing can tell that a project was generated by a different version than the one now patching it. That is the gap noted in `docs/code-audit-2026-11-23.md` (section 4, "Generated projects can't be upgraded") and the groundwork the roadmap's `upgrade-templates` item needs.

This spec adds a small marker file, `.octave.toml`, at the root of every project that `new` creates. It records the generator version and the options chosen. `add-*` commands read it and refuse to patch a project that a newer django-octave generated. Projects generated before this change have no marker and keep working exactly as today.

Out of scope: an upgrade command, backfilling a marker into old projects, and using the marker instead of file detection (see Requirement 4).

## Alignment with Product Vision

Generated projects live for years while the generator changes. A recorded version lets the tool avoid patching a project in a way its own generator would no longer produce, and it is the first step towards upgrading generated projects deliberately instead of by hand.

## Requirements

### Requirement 1 — `new` writes the marker

**User Story:** As a developer, I want my project to record how it was generated, so that later commands and upgrades know what they are dealing with.

#### Acceptance Criteria

1. WHEN `new` creates a project THEN it SHALL write `.octave.toml` at the project root containing a marker format number (`schema = 1`), `generator_version` (the version of the running django-octave), and the options chosen: `database` (`sqlite`, `postgres` or `mariadb`), `docker`, `multitenancy`, and the features `frontend`, `register`, `crud` and `celery`.
2. WHEN `new --frontend`, `--register`, `--crud` or `--celery` are used (or chosen in the prompts) THEN the marker SHALL show those features as enabled; `register` and `crud` SHALL be `false` when `frontend` is `false`.
3. WHEN the file is written THEN it SHALL be valid TOML with a short comment saying it is written by django-octave and should be committed, and `tomllib` SHALL read back exactly the values that were chosen.
4. WHEN `new --force` regenerates into an existing directory THEN the marker SHALL be overwritten like any other generated file, and nothing else in the directory SHALL be deleted (as today).
5. WHEN the generated project is put under version control THEN `.octave.toml` SHALL not be ignored by the generated `.gitignore` or `.dockerignore`.

### Requirement 2 — Only validated values are written

**User Story:** As a maintainer, I want the marker to contain nothing that came from free text, so that it cannot carry injected content.

#### Acceptance Criteria

1. WHEN the marker is written THEN every value SHALL be a boolean, one of the three database names, an integer, or the generator version after it passed a version pattern check; the project name SHALL NOT be written.
2. WHEN the running version cannot be determined (for example the tool runs from a source tree without package metadata) THEN `new` SHALL still succeed and SHALL write `generator_version = "unknown"`.

### Requirement 3 — Optional features keep the marker in step

**User Story:** As a developer, I want `add-celery` and `add-frontend` to be reflected in the marker, so that it stays an accurate record of the options.

#### Acceptance Criteria

1. WHEN `add-celery` succeeds in a project that has a marker THEN `celery` SHALL be `true` afterwards, and no other key SHALL change.
2. WHEN `add-frontend` succeeds in a project that has a marker THEN `frontend` SHALL be `true`, and `register` and `crud` SHALL be set to what the command applied; no other key SHALL change, in particular `generator_version` keeps naming the version that generated the project.
3. WHEN a project has no marker THEN these commands SHALL NOT create one.
4. IF updating the marker fails THEN the command SHALL fail like any other and leave the project unchanged (`rollback_on_error`).

### Requirement 4 — Commands refuse a project from a newer django-octave

**User Story:** As a developer, I want the tool to stop when a project was generated by a newer django-octave, so that an older tool does not patch it in an outdated way.

#### Acceptance Criteria

1. WHEN an `add-*` command runs in a project whose marker `generator_version` is newer than the running version (compared by the numeric release parts, so `0.4.0.dev1` counts as `0.4.0`) THEN the command SHALL exit with code 1 before any file is written, naming both versions and saying to upgrade django-octave.
2. WHEN the marker's `schema` is higher than this version understands THEN the command SHALL refuse the same way, saying the marker was written by a newer django-octave.
3. WHEN the marker is not valid TOML, lacks `schema` or `generator_version`, or has a value of the wrong type THEN the command SHALL exit with code 1 naming the file and the problem, and saying the file can be fixed or deleted.
4. WHEN the marker's version is equal to or older than the running version, or is `"unknown"`, or the running version is unknown THEN the command SHALL proceed with no message.
5. WHEN the marker exists THEN the detection of multitenancy, Celery and the frontend SHALL still use the files in the project as today; the marker SHALL NOT override it, because those files can be changed by hand.
6. WHEN `new` runs THEN it SHALL NOT apply this check (it creates the project).

### Requirement 5 — Projects without a marker are untouched

**User Story:** As a user of an existing project, I want nothing to change for me.

#### Acceptance Criteria

1. WHEN an `add-*` command runs in a project without `.octave.toml` THEN its behavior, output and files SHALL be identical to today's, with no warning and no new file.
2. WHEN the full test suite runs THEN it SHALL pass, and a test SHALL cover a project generated without a marker.

### Requirement 6 — Documentation

**User Story:** As a user, I want to know what the file is and what it does.

#### Acceptance Criteria

1. WHEN the docs are built THEN a page under `docs/concepts/` SHALL describe `.octave.toml`: what it records, that it should be committed, which commands update it, the refusal for a newer version, and that older projects have none.
2. WHEN this spec is implemented THEN the audit notes and the roadmap SHALL mention it where they refer to the generator-version marker.

### Requirement 7 — Nothing else changes

**User Story:** As a user, I want the generated project to be the same apart from the new file.

#### Acceptance Criteria

1. WHEN a project is generated THEN the tree SHALL differ from today's only by the added `.octave.toml` (compared with the same launch method on both sides, as the generator formats files only when `ruff` is on `PATH`).
2. WHEN the full test suite and the opt-in e2e suites run THEN they SHALL pass without weakening an existing test, and `tests/commands/test_option_probe.py` SHALL still pass.

## Non-Functional Requirements

### Code Architecture and Modularity
- **Single Responsibility Principle**: reading, writing and comparing the marker live in one small module; commands do not parse TOML themselves.
- **Modular Design**: `detect_project` is the one place that reads the marker, so every `add-*` command gets the check without repeating it.
- **Dependency Management**: reading uses the standard library `tomllib`; writing is done by hand for this flat structure; no new dependency.
- **Clear Interfaces**: a frozen dataclass for the marker, fully annotated.

### Performance
- One small file read per command.

### Security
- No free text is written (Requirement 2). Reading never executes anything; a malformed file is an error, not a crash.

### Reliability
- A refusal happens before any file is written. A failed marker update leaves the project unchanged.

### Usability
- Refusal messages name both versions and the action to take. The file starts with a comment that explains itself.
