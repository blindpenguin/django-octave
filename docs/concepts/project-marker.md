# The project marker (`.octave.toml`)

`django-octave new` writes a small file, `.octave.toml`, at the root of every project it creates. It records which django-octave generated the project and the options you chose.

```toml
# Written by django-octave. Commit this file; the add-* commands read it.
# It records the version that generated the project and the options chosen.
# django-octave rewrites it when you add a feature, so keep hand edits out.
schema = 1
generator_version = "0.3.0"

[project]
database = "postgres"
docker = true
multitenancy = false

[features]
frontend = true
register = true
crud = false
celery = true
```

**Commit this file.** The generated `.gitignore` and `.dockerignore` do not hide it.

## What it records

| Key | Meaning |
|-----|---------|
| `schema` | Format number of the file itself (currently `1`). |
| `generator_version` | The django-octave version that **created** the project. It does not change when you later run other commands. It is `"unknown"` if the version could not be determined. |
| `[project]` | The choices made at creation: `database` (`sqlite`, `postgres` or `mariadb`), `docker` and `multitenancy`. Docker and multitenancy cannot be added to an existing project, so these stay as they are. |
| `[features]` | Optional parts: `frontend`, `register`, `crud` and `celery`. |

Only booleans, the database name, a number and the version are written. Your project name and other free text never go into the file.

## What keeps it up to date

- [`new`](../commands/new.md) writes it, together with the rest of the project.
- [`add-celery`](../commands/add-celery.md) sets `celery = true`.
- [`add-frontend`](../commands/add-frontend.md) sets `frontend = true`, and `register` to what that run applied (turning registration off removes the route, so the flag follows the run). `--crud` sets `crud = true`; it never turns it off again, because the generated pages stay.

These commands only update a marker that exists. They never create one, and they leave `generator_version` alone.

django-octave rewrites the whole file when it updates it, so comments you add are not kept.

## A project from a newer django-octave is refused

Every `add-*` command reads the marker first. If the project was generated by a **newer** django-octave than the one you are running, the command stops before it writes anything:

```text
This project was generated by django-octave 0.5.0, but you are running 0.3.0. Upgrade django-octave and try again.
```

Versions are compared by their numeric release (`0.4.0.dev1` counts as `0.4.0`, `0.3` equals `0.3.0`, `0.10.0` is newer than `0.9.0`). The same happens when the marker's `schema` is higher than your version understands. A marker whose version is the same, older, or `"unknown"` is accepted without any message.

`new` is not affected: it creates the project, so there is nothing to compare with.

## A file that cannot be read

If `.octave.toml` is not valid TOML, or a key is missing or has the wrong type, `add-*` commands exit with an error that names the file and the problem. Fix the file, or delete it: a project without a marker works exactly as before.

## Projects generated before the marker existed

They have no `.octave.toml`, and nothing changes for them. No `add-*` command creates one, warns about it or behaves differently. Detection of what a project contains (multitenancy, Celery, the frontend) still looks at the files in the project, not at the marker, so a project you changed by hand is understood as it is on disk.

The marker is the groundwork for upgrading generated projects (see the [roadmap](../roadmap.md)): a recorded version and the original options are what an upgrade needs to know.
